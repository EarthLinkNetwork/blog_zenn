# AI開発の共通基盤を、会社の資産にする ── 各人の Claude Code で得た手順と検査を、会社に残す

![AI開発の共通基盤を、会社の資産にする ── 各人の Claude Code で得た手順と検査を、会社に残す](https://raw.githubusercontent.com/EarthLinkNetwork/blog_public/main/images/series-011/hero-ogp.png)

Claude Code を使って、担当者がそれぞれのアプリを開発する。その進め方を考えるとき、私が気になるのは、うまくいった手順や失敗から得た知識が、会社にどれだけ残るかということです。

## 結論

- **担当者の工夫は、本人の環境にあるだけでは会社に残りません。** 各人は引き続き Claude Code で開発し、会社はその周囲に、手順、検査、権限、配布、記録を揃えます。ELN では、この共通基盤をまとめたものを ELN Harness OS と呼んでいます。
- **全社で揃える部分と、チームが育てる部分を分けます。** 利用者の管理や配布は全社で持ち、業務に合わせた手順はチームが Plugin として公開し、必要なチームが確かめてから採用します。
- **記録と制御、AI の指摘と再現した事実を分けて扱います。** 利用量を記録しても上限で止まるわけではありません。AI のペルソナ同士が同意しても、利用者が同じ問題に困ったことにはなりません。

## 1. 担当者の工夫を、会社に残す

ある担当者がレビューの精度を上げても、その方法が本人の環境にしかなければ、別の担当者は同じ試行錯誤をします。チームごとに独自の開発基盤を作れば、今度は設定や更新方法が増えていきます。

そこで、開発に使う共通の仕組みを、会社の資産として育てたいと考えています。各人は引き続き Claude Code で開発します。会社はその周囲に、手順、検査、権限、配布、記録を揃えます。ELN Harness OS は、この共通基盤をまとめたものです。OS という名前には、開発環境を支える土台という意味を込めています。

なお、ELN Harness OS は ELN の開発基盤につけた名前で、一般に確立した標準の名前ではありません。本稿の「ハーネス」は、AI が開発を進め、その結果を確かめるための手順、検査、設定、記録をまとめた仕組みを指します。

ELN Harness OS は、次の 4 つの層で設計しています。

![ELN Harness OS の 4 つの層。01 全社管理基盤（認証・権限、カタログと採用しているバージョン、実行記録、接続経路ごとの費用・上限、更新と停止の管理）、02 共通Plugin（実装手順、コード検査、Persona QA、結果の形式）、03 チームのPlugin（予約業務・顧客管理・設計レビューなどの専門手順）、04 各PCと各製品（各人のClaude Codeに採用したPluginを接続、公開するかは製品責任者が決める）（上原作成の図）](https://raw.githubusercontent.com/EarthLinkNetwork/blog_public/main/images/series-011/fig1-four-layers.png)

- **01 全社管理基盤**: 認証と権限、使える Plugin の一覧（カタログ）、採用しているバージョン、実行の記録を持つ層です。接続の経路ごとの費用と上限、更新と停止もこの層で管理する設計です。
- **02 共通 Plugin**: 実装の手順、コードの検査、Persona QA、結果の形式など、ELN の標準の部品と、会社で共通の開発ルールを置く層です。
- **03 チームの Plugin**: 予約業務、顧客管理、設計レビューなどの専門の手順を置く層です。公開したチームが保守し、使う側のチームが確かめてから採用する設計です。
- **04 各 PC と各製品**: 各人の Claude Code に、採用した Plugin をつなぐ層です。製品のリポジトリ、仕様、テストは製品側にあり、公開するかどうかは製品の責任者が決めます。

開発そのものは、これまでどおり各人の PC で続けます。既にある Claude Code と Plugin の仕組みに、全社の管理と運用を組み込む形です。

## 2. 全社で揃える部分と、チームが育てる部分

全社で持つのは、利用者の管理、許可する接続先、共通 Plugin の配布、利用状況の記録、検査の基本手順です。チームは、業務や技術に応じた Skill、レビュー手順、外部ツールとの接続を Plugin として公開します。必要なチームが、その Plugin を導入します。

例えば、予約管理と顧客管理では、画面も業務ルールも異なります。それでも「権限のないデータを返さないことを検査する」という手順は共有できます。どの予約や顧客を誰が見られるかは、各プロダクトの仕様に残します。

共通化の対象は、別の現場でも役立つと確認できたものに絞ります。全社基盤の担当者がすべての機能開発を引き受ける必要はありません。プロダクト責任者は、要件、優先順位、受入条件、公開後の成果を担い続けます。

領域ごとに並べると、分け方は次のようになります。

| 領域 | 全社基盤で共通化する | Plugin で拡張する |
|---|---|---|
| 利用と権限 | 利用者・所属・役割、許可する接続先と実行条件 | 業務に必要な入力とツール、要求する権限の宣言 |
| 配布と更新 | カタログ、評価の状態、採用しているバージョン、更新の通知と配布 | Skill・Agent・Hook・接続の定義、対応するバージョンと依存関係 |
| 実行と記録 | 実行 ID、履歴、再実行の条件、ログの保管と検索 | 作業の分解と業務の手順、報告書や成果物の形式 |
| 品質と判断 | 共通の CI、承認の経路、検査の記録の保管 | 製品ごとの受入条件、ペルソナと検査項目 |
| 費用と停止 | 接続経路ごとの集計と予算、利用上限と停止の設定 | 使うモデルと処理の内容、必要な時間と利用量の見積もり |

必ず守らせたい方針は、組織が管理する設定や CI、接続先のサービスで制御します。業務ごとの仕様は製品側に残し、別のチームでも使える手順から共通化していきます。

## 3. 置き場所と更新方法まで決める

共通 Plugin の中身は社内の Git リポジトリで管理し、社内 Marketplace から各人の Claude Code へ配布します。製品固有の仕様やテストは、製品のリポジトリに置きます。全社で必須にする設定は、管理者が配布する Managed settings で扱います（[Claude Code 公式: 組織での Plugin の管理](https://code.claude.com/docs/en/plugins/org)）。

更新は、現場の問題を再現する検査を作り、変更案をレビューし、代表的な製品で試してから配布します。試験利用するグループと通常利用するグループを分け、問題が出た場合に戻すバージョンも決めます。Plugin の公開者には、説明だけでなく、保守担当、対応環境、検査結果、変更履歴を用意してもらいます。

なお、Plugin にルール文書を入れれば、すべてが自動で適用されるわけではありません。Claude Code に読ませる指示と、Hooks や CI で実行する検査には、それぞれの設定が必要になります（[Claude Code 公式: Plugin の構成要素](https://code.claude.com/docs/en/plugins/components)）。たとえば、Plugin の一番上の階層に置いた CLAUDE.md は自動では読み込まれません。常に守らせたい指示は、製品のリポジトリや組織の設定の側に書きます。

製品のリポジトリの中でも、共有する設定と個人の設定は置き場所を分けます（[Claude Code 公式: settings](https://code.claude.com/docs/en/settings)）。

- **CLAUDE.md**: 共通の手順への参照と、製品固有の指示。製品のリポジトリで共有します。
- **.claude/settings.json**: 共有する Hooks、権限、Plugin などの設定。これも製品のリポジトリで共有します。
- **.claude/settings.local.json**: 個人がその製品で使う設定や、試している設定。Git には入れません。
- **~/.claude/settings.json**: 各人の PC にあるユーザーの設定。個人で管理します。

チームの中で試す段階では、共通のリポジトリを Git の submodule で各製品に取り込む方法もあります。全社に広げるときは、社内 Marketplace の Plugin に移します。そのとき、同じ Skill や検査を submodule と Plugin の両方から読み込ませないようにします。

## 4. チームの Plugin を、別のチームが採用する

チームが作った Plugin は、公開から採用まで、次の順で進めます。

1. **チームが公開する**: 保守担当と配布物を登録します。
2. **共通の評価をする**: 検査、依存関係、必要な権限を確かめます。
3. **限定して試す**: 別のチームの実案件で確かめます。
4. **安定版に登録する**: 評価の結果と変更履歴を公開します。
5. **製品が採用する**: 自分の製品で検査し、使うバージョンを固定します。

![チームのPluginを、別のチームが採用する流れ。チームが公開→共通評価→限定試用→安定版に登録→製品が採用。公開時に添える情報は、保守担当・対応するバージョン・必要な権限・評価記録・既知の制約・更新と復旧（上原作成のスライド）](https://raw.githubusercontent.com/EarthLinkNetwork/blog_public/main/images/series-011/fig2-plugin-adoption.png)

公開するときは、保守担当（問い合わせと修正の窓口）、対応するバージョン（Claude Code や Plugin への依存）、必要な権限（ファイル・API・Secrets）を添えます。評価の記録（課題・期待値・実行結果）、既知の制約（使えない条件）、更新と復旧の方法（変更履歴と戻せるバージョン）も添えます。社内 Marketplace の作り方と保守は、Claude Code の公式の文書にあります（[Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace)）。

公開したチームは、品質と保守を担います。導入する側は、受け入れと、採用するバージョンを決めます。

全社基盤がすべての変更を抱え込むと、現場の待ち時間が増えます。公開したチームに保守の責任を置き、製品の責任者には採用と受け入れの権限を残します。製品のバックログと、共通基盤の改善のバックログは、それぞれ管理します。

## 5. サーバーに任せる仕事

各人の Claude Code が実装を進める一方、共通の自動検査や検証環境、社内ツールへの接続には共有サービスを使います。利用者や予算を一元管理するなら、モデルへの通信を受け付ける Gateway も候補になります（[Claude Code 公式: Gateway](https://code.claude.com/docs/en/gateways)）。

最初から大きなサーバーを用意する必要はありません。Claude Code では、編集とコマンドの実行は各人の PC で行われ、推論は契約しているモデルのサービスが行います（[How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)）。最初に用意するのは、共通の Git リポジトリ、共通の CI、検証環境です。専用のサーバーが要るのは、次のような場合です。

- **CI に社内への接続や独自の環境が要る**: CI の処理を動かすマシン（Runner）を専用に用意します。標準では GitHub が用意するマシンで動きます（[GitHub-hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)）。
- **各人から共通の社内機能を呼ぶ**: 社内の検索や API への接続を、共有サービスとして設けます。MCP は接続の方式で、ハーネス全体を置く場所ではありません。
- **全社で運用する**: 設定と状態のデータベース、CI や QA を作業ごとに動かして止められる実行の仕組み、ブラウザでの検証環境、ログや画面を実行 ID に結び付けて保存する場所を、役割ごとに配置します。必要なら LLM Gateway も加えます。

共通の手順を配布するためだけに、推論用の GPU は要りません。作業用の環境と本番の環境は分けておきます。

## 6. 利用量の記録と、上限で止めることを分ける

ここでは、利用量を記録することと、上限で実行を止めることを分けて考えたいと思います。OpenTelemetry で利用状況を集計しても、その記録だけで予算超過を防げるわけではありません。強制する上限が必要なら、対象の通信が必ず予算の確認を通る経路を設けます（[Gateway](https://code.claude.com/docs/en/gateways)・[Monitoring](https://code.claude.com/docs/en/monitoring-usage)）。

また、会社の API 契約を使う Gateway と、各人のサブスクリプションで使う方式では、課金の扱いが異なります。既存契約をどう扱うかを決めてから、構成を選びます。

![予算は、記録と実行制御を分けて扱う。個人のClaude Code契約は取得できるログとOpenTelemetryで利用状況を集約、管理するAPI経路はGatewayで割当予算と実行条件を照らし合わせ新規要求の停止を適用。API経路での管理は 1 認証・照合、2 予算を予約、3 実行、4 精算（上原作成のスライド）](https://raw.githubusercontent.com/EarthLinkNetwork/blog_public/main/images/series-011/fig3-budget-record-and-stop.png)

個人の Claude Code の契約では、取得できるログで利用状況を確かめ、OpenTelemetry で全社の記録へ集めます。契約費は月単位で、実行にかかった費用は取得できる範囲でしか分かりません。

管理する API の経路では、Gateway で利用者、製品、モデルを確かめ、割り当てた予算と実行の条件を照らし合わせます。新しい要求を止めるのは、この経路で行います。流れは次の 4 つです。

1. **認証と照合**: 利用者と製品を確かめます。
2. **予算を予約する**: 要求の上限の分を先に確保します。
3. **実行する**: 時間と回数にも上限を設けます。
4. **精算する**: 実績で記録を更新し、確保した分の残りを戻します。

予約と精算は、基盤の側の管理の処理です。集計の遅れと、並列で動いている実行の費用も考えておきます。個人の契約のすべての経路を、共通の Gateway で管理できる前提にはしません。

## 7. やり直しは、操作の種類ごとに扱う

やり直しにも区別が必要です。通信失敗の再試行や、検査失敗後の修正手順は共通化できます。一方、予約を確定したり、外部へ通知したりした後の取消は、その処理に応じた復旧手順が要ります。再実行しても二重登録しない仕組みまで、製品側と取り決めます。

| 対象 | やり直す単位 | 始める前に決めること |
|---|---|---|
| API の再試行 | 一時的な通信や応答のエラー、同じ処理の再送 | 上限の回数・待ち時間・合計時間、費用の上限、重複実行を避ける ID |
| 実装のやり直し | 別の作業領域で変更を作り直し、検査結果を比べて採用する | 開始時のコードと使ったバージョン、既存の手作業を残す範囲 |
| 外部への変更の取消 | データベースの更新、公開、外部 API への書き込みを、操作ごとに取り消す | 対象の ID・重複の防止・取消の権限、取り消せない場合の確認先 |

Claude Code のチェックポイント（作業の途中の状態に戻す機能）だけでは、外部サービスへの変更は戻せません（[Checkpointing](https://code.claude.com/docs/en/checkpointing)）。外部への変更は、操作ごとに取り消せる範囲を確かめておきます。

## 8. ペルソナのレビューを、ブラウザでの検査につなげる

QA では、プロジェクト概要から想定利用者を整理し、複数のペルソナに画面をレビューさせます。初めて使う人、日々大量の処理をする担当者、キーボード操作を中心に使う人では、気になる点が違うはずです。

予約と受付のポータルを例にすると、次のようになります。人物像と論点は、説明のためのサンプルです。

| ペルソナ | 達成したいこと・利用条件 | レビューで出る論点 |
|---|---|---|
| 初回の参加者 | 移動中に、スマートフォンから初めて予約する | 確定の前にキャンセルの条件が分かるか |
| 忙しいイベント運営者 | 慣れた操作で、複数の予約をすばやく処理する | 毎回の説明で操作が止まらないか |
| キーボードで使う人 | PC でマウスを使わずに入力し、確認する | 説明を閉じた後、操作の位置が戻るか |
| 当日の受付担当 | 混雑する時間帯に、予約の状態を確かめる | 再送と別の予約を区別できるか |

ペルソナは、年齢や肩書きだけで決めません。目的、経験、利用環境から観点を作ります。

各レビューを先に集め、討論では指摘の重複、意見の違い、確認すべき操作を整理します。その後、Playwright などでブラウザを動かし、仕様と照合します。対象のバージョン、権限、初期データ、操作、期待値、実行した結果を残します（[Playwright: Best Practices](https://playwright.dev/docs/best-practices)）。

## 9. 討論の結果を、仕様と検査に分ける

例えば、予約確認の画面にキャンセルの条件をどこまで出すかで、意見が分かれたとします（発言と結論はサンプルです）。初回の参加者は「条件を全部読んでから確定したい」、忙しい運営者は「長文だと日時や金額が埋もれる」と言います。

採用の候補は、「期限と料金の要点を表示し、全文はその場で開けるようにする」です。ここから、検査に回すものと、人の判断に回すものを分けます。

- **検査に回す**: 全文を閉じたらフォーカスが戻る。条件の要点が確定の前に表示される。
- **人の判断に回す**: キャンセル料の計算、期限の基準の時刻、複数の予約を認める条件。

最初から他の意見に合わせず、各ペルソナが先に観点を出します。対立や少数の意見は、多数決で消さずに記録に残します。

討論の合意は、正解の保証にはなりません。似たモデル同士の討論が、共有する誤解に収束し得ることを検討した研究があります（[Estornell・Liu、2024](https://papers.nips.cc/paper_files/paper/2024/file/32e07a110c6c6acf1afbf2bf82b614ad-Paper-Conference.pdf)）。LLM に評価させるときの偏りを検討した研究（[Zheng ほか、2023](https://arxiv.org/abs/2306.05685)）もありますが、これはチャットの応答を評価する研究で、UI の有効性を実証した資料ではありません。AI の討論は、確認する候補を整理するために使います。

## 10. QA の結果は、根拠の種類で分ける

「AI が指摘した」「ブラウザで再現した」「人の判断が必要」は、画面でも分けて表示します。AI 同士が同意しても、実ユーザーが同じ問題を経験したことにはなりません。使いやすさの評価や、アクセシビリティの一部には、人による確認を組み込みます（[W3C WAI: Selecting Web Accessibility Evaluation Tools](https://www.w3.org/WAI/test-evaluate/tools/selecting/)）。

![QAの結果は、根拠の種類で分ける。Personaからの指摘、再現確認済み、不安定、人の確認待ち、修正確認済みの 5 つの状態ごとに、何が分かったかと次の対応を並べた表（上原作成のスライド）](https://raw.githubusercontent.com/EarthLinkNetwork/blog_public/main/images/series-011/fig4-qa-evidence-types.png)

「再現確認済み」と書けるのは、仕様の期待値と実行の記録がそろっている時だけです。再試行で通ったもの、まだ実行していないもの、判断を待っているものは、分けて表示します。

同じモデルが演じる複数のペルソナを、独立した利用者として数えることもしません。自動の検査だけで、WCAG 全体に適合していると宣言することもしません。

人が時間を使うのは、利用者の観察、業務上の例外、優先順位、公開の判断です。

## 11. 効果を確かめる指標

生成したコード量や Plugin の本数だけで、成果を判断しません。同程度の難易度と受入条件の案件を比べ、次の指標を記録します。

| 指標 | 確認すること |
|---|---|
| 受入までの日数 | 実装開始から責任者の受入までの時間 |
| 初回受入率 | 最初の提出で条件を満たした割合 |
| 再発率 | 一度直した問題が別の変更・製品で再発していないか |
| 人の確認時間 | QA の反復作業が減り、判断や実利用者の観察に時間を使えているか |
| 変更失敗と復旧時間 | 共通 Plugin の変更で影響が広がっていないか、戻せるか |
| 受入できた変更あたりの費用 | モデル利用だけでなく、再実行・CI・人の確認も含める |

指標の定義をそろえる際は、[DORA のソフトウェアデリバリー指標](https://dora.dev/guides/dora-metrics/)も参考にします。アプリケーションごとに時間を追って比べ、業務や条件が大きく違うチームの順位づけには使いません。

比べられるように、1 回の実行ごとに次の記録を残します。

- **対象**: 製品名、依頼の内容、受入条件。
- **構成**: 製品のコード、ハーネス、環境、モデルのそれぞれのバージョン。
- **結果**: 検査の結果、変更案、人の手直し、失敗の理由。
- **負担**: 作業の時間と、把握できる利用量と費用。

費用は、Claude Code の契約費、必要な API の費用、共通環境の費用を分けて把握します。

## 12. 改善を共有する流れ（説明用の例）

ここからは説明用の例で、ELN で起きた障害や導入の実績を示すものではありません。

ある製品で、権限のない利用者にもデータを返す問題が見つかったとします。まず製品側を修正し、同じ問題を再現するテストを残します。次に、ほかの製品にも使える確認手順を共通 Plugin へ移し、別のチームで試します。採用するバージョンを固定し、問題があれば元のバージョンへ戻せる状態で配布します。

たとえば、担当するイベントの予約を CSV で出力する機能で、担当外の予約まで出力されていたとします。直した後は、別の製品でも同じことが起きるかを確かめます。どの予約を誰が見られるかという固有の条件は、製品側に残します。共通のリポジトリに足すのは、「担当外のデータを返さない」ことを確かめる手順です。別の製品では、その製品の権限のルールに合わせて、同じ手順の検査を動かします。

ここで更新するのは、手順、検査、設定です。AI のモデルを学習し直すわけではありません。

## 13. ELN が支援する導入の進め方（提案）

ELN では、この開発基盤を、導入する会社の開発環境に合わせて組み込むことを提案しています。最初に既存の手順と困り事を整理し、対象プロダクトを一つ決めます。次に共通の検査と Plugin 配布を整え、別の担当者、別のプロダクトでも使えるかを確かめます。その結果を見ながら、利用者管理、予算管理、QA の自動化を広げていきます。

段階と、次へ進む条件は、次のように考えています。

1. **2 つのチームで試す**: 各人の Claude Code に接続し、小さな機能を 1 件開発します。同じ手順で実装と検査を再現でき、受入条件と記録が残れば次へ進みます。
2. **共通 Plugin にする**: 繰り返す作業を Plugin にし、保守担当、評価の課題、バージョンを登録します。別のチームが口頭の補足なしで使えれば次へ進みます。
3. **管理につなぐ**: 認証、権限、ログ、費用をつなぎ、管理する API の経路を決めます。停止の条件と、更新と復旧の窓口が決まれば次へ進みます。
4. **広げる**: 対象を広げ、採用するバージョンを段階的に更新します。前のバージョンへ戻す方法を確かめてから、運用を各製品の責任者に引き継ぎます。

最初の目標は、誰が実行しても、同じ手順で 1 件の変更案と検査結果を出せることです。

導入後も、各プロダクトで見つかった改善を基盤へ戻します。会社に残したいのは、次の担当者がそのまま使える手順と検査です。それを保守する仕事まで、開発体制の中に組み込みたいと考えています。

技術仕様は 2026 年 11 月 25 日に公式資料で確かめました。使える機能は Claude Code のバージョンと契約によって異なるため、導入するときに改めて確かめます。

## 用語

- **Claude Code**: Anthropic の AI のコーディングツール。開発者の PC で動き、コードの編集やコマンドの実行を行います。
- **ハーネス**: AI が開発を進め、その結果を確かめるための手順、検査、設定、記録をまとめた仕組み。
- **ELN Harness OS**: ELN が自社の開発基盤につけた名前。一般に確立した標準の名前ではありません。
- **Plugin**: Claude Code に Skill、Agent、Hooks、外部との接続などをまとめて追加する仕組み。
- **Skill**: AI が作業の中で呼び出して使う、手順をまとめた部品。
- **Hooks**: ファイルの編集の後など、決まった時に自動で検査などを動かす Claude Code の設定。
- **社内 Marketplace**: 社内で作った Plugin を一覧にし、各人の Claude Code に配布する場所。
- **Managed settings**: 管理者が全社に配布する Claude Code の設定。各人の設定ファイルより優先されます。
- **CI**: コードを変えるたびに、自動でテストや検査を実行する仕組み。
- **Gateway**: モデルへの通信をいったん受け付け、利用者の確認、利用量の記録、上限の適用などを行う中継の仕組み。
- **OpenTelemetry**: ソフトウェアの利用状況や動作の記録を集めるための標準の仕組み。
- **MCP**: Claude Code から社内のツールや外部のサービスにつなぐための接続の方式。
- **ペルソナ（Persona QA）**: 目的、経験、利用環境を決めた想定利用者。Persona QA は、AI にペルソナとして画面をレビューさせる QA の進め方です。
- **Playwright**: ブラウザを自動で操作し、画面の動きを確かめるテストのツール。
- **WCAG**: Web のアクセシビリティ（障害の有無などにかかわらず使えること）の国際的な指針。
- **DORA**: ソフトウェアを届ける力を測る指標を研究している取り組み。
- **Git submodule**: あるリポジトリの中に、別のリポジトリを決まったコミットで取り込む Git の機能。
